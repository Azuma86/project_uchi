# ADR 006: 経費の集計をどう実装するか

- ステータス: 採用
- 日付: 2026-09-04

## 状況

経費画面で以下を表示したい。

- 今月の承認済み合計
- 今月の承認待ち合計と件数
- カテゴリ別の合計
- 月別の一覧

Firestore には SQL の `SUM()` や `GROUP BY` がありません。どう実現するか。

## 決定

**その月の経費を 1 クエリで取得し、アプリのメモリ上で合計します。**
ただし「件数だけ欲しい」場所では **aggregate query の `count()`** を使います。

## 検討した選択肢

### A. 都度集計 (クエリして足す) ← 採用

```ts
const snap = await expensesCol(familyId).where('yearMonth', '==', '2026-09').get();
// 取得したドキュメントをループして合計する
```

**利点**
- **常に正確**。ズレが起きない
- 実装が単純 (数十行)
- 一覧表示に使うデータと同じものを使い回せる (追加の read がゼロ)

**欠点**
- read 回数 = その月の経費件数

**この欠点が問題にならない理由**

家族の経費は月に多くて数十件です。
Firestore の無料枠は **1 日 50,000 read**。
経費画面を 1 回開くと 30 read として、1 日 100 回開いても 3,000 read。
無料枠の 6% です。**問題になりません。**

### B. 集計用ドキュメント (カウンタ)

`families/{familyId}/summaries/2026-09` のようなドキュメントを持ち、
経費の作成・承認・削除のたびにトランザクションで加減算する方式。

**利点**
- 集計の read が常に 1 回

**採用しなかった理由**
- **書き込みが重くなる**。経費 1 件の承認が「経費の更新 + 集計の更新」になり、
  トランザクションの範囲が広がります
- **ズレたときの修復が面倒**。
  一度でもバグや障害でカウンタがずれると、
  再計算スクリプトを書いて直す必要があります
- **状態遷移が複雑**。draft → pending → approved → (却下されて) rejected → 再申請…
  という遷移のたびに、どのカウンタをいくつ動かすかを正しく書く必要があります。
  ここは間違えやすく、間違えると家計の数字が狂います
- 家族数人の規模では、この複雑さに見合う read の削減量がありません

**必要になる条件**: 1 か月の経費が 1,000 件を超えたら再検討します。

### C. Firestore の aggregate query (`count` / `sum` / `average`)

Firestore には集計クエリがあり、ドキュメント本体を読まずに集計できます。
課金も「読んだドキュメント数」ではなく、
**スキャンしたインデックスエントリ 1,000 件につき 1 read** と大幅に安くなります。

**部分的に採用しました。**

```ts
// 承認待ち件数 (ナビゲーションのバッジ) — ドキュメントを読まない
const snap = await expensesCol(familyId).where('status', '==', 'pending').count().get();
```

`sum()` を使わなかったのは、
**経費一覧の表示にどのみち全ドキュメントが必要だから** です。
一覧のために読んだデータをそのまま合計すれば、追加コストはゼロです。
`sum()` を別に呼ぶと、かえってクエリが 1 回増えます。

一方、承認待ち件数は **全ページのナビゲーションに出る** ため、
ドキュメント本体が不要な `count()` が効きます。

## `yearMonth` フィールドを持つ理由

購入日で月を絞るには、本来は範囲クエリが必要です。

```ts
.where('purchaseDate', '>=', 月初).where('purchaseDate', '<', 翌月初)
```

代わりに `yearMonth: "2026-09"` という文字列を非正規化して持たせ、
**等価条件 1 つ** で引けるようにしました。

| | 範囲クエリ | 等価クエリ (yearMonth) |
|---|-----------|----------------------|
| 複合インデックス | 必要かつ大きい | 小さい |
| 他の条件との組み合わせ | 範囲は 1 フィールドまでという制約に当たりやすい | 組み合わせやすい |
| タイムゾーン | クエリのたびに JST→UTC 変換が要る | 書き込み時に 1 回だけ変換すればよい |

最後の点が実は一番重要です。
`yearMonth` は **書き込み時に JST 基準で確定** するので、
「月末 23:30 の買い物が翌月に計上される」といったタイムゾーン起因のバグを
構造的に防げます。

## 「下書きは本人にしか見せない」の実装

Firestore の Security Rules は、クエリ全体が安全であることを
静的に証明できないと拒否します。
`status != 'draft' || applicantUserId == uid()` のような OR 条件は
クエリとして表現しにくいため、

- **Rules**: 家族メンバーなら経費コレクションを読める
- **サーバー**: 取得後に `visibleExpenses()` で他人の下書きを除外する

としました。下書きは「まだ申請していないメモ」であり、
家族内で見えても実害が小さいこと、
そして経費件数が少なくメモリ上のフィルタで十分なことが理由です。

## 結果

- 集計コードは `getMonthlySummary()` の 50 行程度に収まりました
- カウンタのズレという運用上の悩みが発生しません
- 経費が激増したら方式 B へ移行する余地を残しています

## 見直す条件

- 1 か月の経費が 1,000 件を超えた
- 「過去 3 年の月別推移グラフ」のように、多数の月をまたぐ集計が必要になった
  (この場合は集計ドキュメント、あるいは BigQuery へのエクスポートを検討)
