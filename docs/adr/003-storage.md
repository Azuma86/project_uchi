# ADR 003: なぜ写真を Firestore ではなく Cloud Storage に保存するか

- ステータス: 採用
- 日付: 2026-09-04

## 状況

家族アルバムと領収書の画像を保存する必要があります。

- スマホで撮った写真は 1 枚 3〜8MB
- 年間で数百〜数千枚になりうる
- 家族以外には絶対に見せたくない

## 決定

**画像の実体は Cloud Storage に保存し、Firestore にはメタデータ (パス・撮影日時・キャプション) だけを持ちます。**

さらに以下を組み合わせます。

1. バケットは非公開 (`public_access_prevention = enforced`)
2. ブラウザ側で縮小・WebP 変換してからアップロード
3. アップロードもダウンロードも **署名付き URL** でブラウザと GCS が直接やり取りする
4. 保存先パスは必ずサーバーが決める (`families/{familyId}/photos/{uuid}.webp`)

## 検討した選択肢

### A. Firestore に画像を Base64 で保存

**却下。** Firestore の 1 ドキュメントは最大 **1MiB** です。
スマホの写真 1 枚すら入りません。
仮に縮小して入れたとしても、

- Base64 化でサイズが約 1.33 倍に増える
- 一覧表示のたびに画像本体を読むことになり、Firestore の read 料金が跳ね上がる
- Firestore の保存料金 (GB あたり) は Cloud Storage より高い

と、あらゆる面で不利です。

### B. Cloud Storage に保存 ← 採用

Cloud Storage は「大きなファイルを安く置く」ために作られたサービスです。

- 保存料金が安い (Firestore の数分の 1)
- ファイルサイズの上限が実質無い
- 署名付き URL でアクセス制御できる
- ライフサイクルルールで古いデータの自動削除ができる

## アップロード経路の設計

「ブラウザ → Cloud Run → GCS」ではなく
**「ブラウザ → (署名付き URL) → GCS」** を選びました。

```
[1] ブラウザ  --- Server Action --->  Cloud Run
                「写真をアップロードしたい (webp, 320KB)」
[2]           <--- 署名付き PUT URL ---
                 保存先パスはサーバーが決める
[3] ブラウザ  --- PUT (画像本体) --->  Cloud Storage
                 Cloud Run を経由しない
[4] ブラウザ  --- Server Action --->  Cloud Run
                「アップロード完了。Firestore に登録して」
                 サーバーは GCS 上の実物を検証してから登録
```

**Cloud Run を経由しない利点**

- 画像が Cloud Run のメモリと CPU を使わない (= 課金が増えない)
- Cloud Run のリクエストサイズ上限 (32MB) に縛られない
- 回線が遅くてもタイムアウトしにくい

**安全性をどう保つか**

- パスはサーバーが `families/{自分の家族ID}/photos/{UUID}` で生成するので、
  クライアントは他家族の場所へ書けません
- 署名付き URL は 10 分で失効し、Content-Type も署名に含まれます
- アップロード後、サーバーが **GCS 上の実物** のサイズと Content-Type を検証します
  (クライアントの自己申告を信用しない)

## ブラウザ側で圧縮する理由

`src/lib/images/process.ts` で、アップロード前に Canvas で縮小・WebP 変換しています。

| 効果 | 内容 |
|------|------|
| 通信量 | 5MB → 約 300KB。スマホのギガを消費しない |
| Cloud Run | サーバーで画像処理をしないので CPU 時間の課金が発生しない |
| Storage | 保存量が 1/15 程度になり保存料金が下がる |
| プライバシー | Canvas で再エンコードすると **EXIF が消える** |

最後の点が重要です。スマホの写真には **GPS 座標** (自宅の位置) が
埋め込まれていることがあります。再エンコードによってこれらは完全に除去されます。
一方、失いたくない「撮影日時」だけは変換前に読み出して Firestore に保存しています
(`src/lib/images/exif.ts`)。

## サムネイルを別ファイルにする理由

一覧表示で 1600px の画像を 60 枚読むと、通信量も表示速度も厳しくなります。
アップロード時に 400px 版も作って別オブジェクトとして保存し、
グリッド表示ではそちらだけを使っています。

## 結果

- 保存料金と通信量を最小限に抑えられました
- 位置情報の流出リスクを設計レベルで排除しました
- 引き換えに、アップロードの手順が 3 ステップになり、
  クライアント側のコードが少し複雑になりました

## 見直す条件

- 動画を扱うようになったら、再生用のトランスコードが必要になります
  (Cloud Run ジョブか Transcoder API を検討)
- 写真が数万枚規模になったら、
  サムネイルを Cloud CDN でキャッシュすることを検討します
